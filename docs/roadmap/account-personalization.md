# アカウント登録・パーソナライズ 設計書(ロードマップ)

- 日付: 2026-09-17
- 位置づけ: 今後の展望として検討した設計。実装計画(タスク分解)はこの設計を元に着手時に別途作成する
- 分類: アーキテクチャレベル(新規サブシステム追加、既存Workerの責務拡張を伴う)

## 背景・目的

現状のRSS Summaryは、全訪問者に対して同一の「今日のダイジェスト」を配信する静的サイトである。本設計は、Googleアカウントでのログインを起点に、ユーザーごとの興味・カスタムフィード・AI要約の観点をパーソナライズできる機能を追加し、将来的なStripe課金による収益化の土台を作ることを目的とする。

前提として、以下を確認済み:
- 想定ユーザー規模: 小規模な複数ユーザー(知人等)からスタートするが、誰でも自己登録可能な公開サービスとして設計する
- 認証・DB・課金のいずれも、知人数名規模はもちろん相当な規模までクラウド利用料は無料に収まる(Google OAuth自体は常に無料、Cloudflare D1/Workersは利用量ベースの無料枠、Stripeは決済手数料のみで固定費なし)
- 「Webapp化」は独立した目的を持たない(パーソナライズ機能を実現するためのAPI+ログイン状態そのものであるため、本specに統合)

## 認証方式

**Google OAuthを自前実装(Arctic + Cloudflare D1)する。** Firebase Auth・Clerk等のホスト型/マネージド認証サービスは採用しない。

比較検討した結果:

| 方式 | 無料枠 | 備考 |
|---|---|---|
| **採用: Arctic+D1(自前)** | 月間ユーザー課金という概念自体がない | Cloudflareスタックに閉じ、依存が最小。Stripe課金を前提にしても3DS/SCA・税・全対応国等の制約がない |
| Firebase Auth | 5万MAUまで無料 | 別途GCP/Firebaseプロジェクト管理が必要。WorkersでのAdmin SDK利用は`nodejs_compat`前提か非公式検証ライブラリが必要 |
| Clerk(+Clerk Billing) | 5万MRUまで無料 | 課金一体化で実装量は減るが、Stripe手数料に加え取引ごと0.7%上乗せ。Billingは2026年時点でBeta、3DS/SCA未対応、税/VAT未対応、USD限定 |

`Arctic`(edge-native・軽量なOAuth 2.0クライアントライブラリ)でGoogleへの認可コードフローを実装し、ユーザー・セッションはCloudflare D1に自前で保存する。

## データ最小化方針

個人情報の保存は必要最小限に留める:

- `users`テーブルにemail・display_nameを**保存しない**。ログインキーはGoogleの`sub`(不変の識別子)のみ
- 決済時のメールアドレスはStripe Checkout側で収集・保持してもらい、こちらでは複製しない(Stripeを個人情報の一次情報源とする)
- メール配信機能(有料)を実際に使うユーザーのみ、配信先アドレスを別テーブルに最小限保持する
- UI上の表示名等が必要な場合は、ログイン時にGoogleから取得しセッション内でのみ使用し、DBには保存しない
- ブックマーク・既読・カスタムフィード・AI指示などの行動データは`google_sub`に紐づけて保持する(機能上必須なため)。アカウント削除時に一括削除できるようにする

## 機能セット: 未登録/無料/有料の3段階モデル

情報量(コンテンツの種類・件数)は全層に開放し、**AI要約の深さ・パーソナライズ度合いだけが段階的に上がる**軸で設計する。ジャンル(Arxiv論文等)を増やすほど、この3段階すべてが厚くなる構造にする。

| 層 | 位置づけ | 中心となる価値 |
|---|---|---|
| **未登録** | 包括的な情報まとめサイト | テック記事+Arxiv論文等、対応ジャンルすべてに一行あらすじ付きでアクセス可能。本文は元記事へ誘導する現行の形を維持 |
| **無料登録** | 包括的な情報管理サイト | 興味カテゴリ選択・ブックマーク・既読管理など、大量の情報を「整理する」機能が中心。AI要約自体は定型(未登録と同水準)のまま |
| **有料** | パーソナライズ要約サイト | AI要約の精度・厚みが上がり、要約だけで完結できるレベルに近づく(元記事へのクリックが減っていく体験) |

**未登録(現行維持)**
- 全ジャンルの記事に、定型の一行あらすじ(現行同様)
- カテゴリ別ピックアップ(現行同様)

**無料登録で追加**
- 興味カテゴリの選択(選んだカテゴリのみ/優先表示)
- 記事の保存・ブックマーク
- 個人ごとの既読/未読管理(サイト全体の既読state`state/read-guids.json`とは別に、ユーザー単位で管理する)

**有料(Stripe課金)で追加**
- カスタムフィード追加(既存フィードに加え、ユーザー自身が登録したRSSも収集対象にする)
- **パーソナライズ型AI要約**(有料機能の主軸): ユーザー固有の観点での記事収集・選定・要約をGeminiに指示できる。例:「セキュリティ関連を優先して」等の自由記述の指示をプロンプトに反映する
- メール配信(毎朝のダイジェストをWeb閲覧に加えメールでも受け取れる)
- アーカイブ無制限・全文検索(現行の14日間表示制限を撤廃し、過去分を横断検索できる)

## データモデル(Cloudflare D1、概要)

```
users(id, google_sub, created_at)
sessions(id, user_id, expires_at)
subscriptions(user_id, stripe_customer_id, stripe_subscription_id, status, plan, current_period_end)
user_category_prefs(user_id, category, enabled)
bookmarks(id, user_id, article_link, article_title, saved_at)
user_read_state(user_id, article_guid_hash, read_at)
custom_feeds(id, user_id, feed_url, created_at)              -- 有料のみ
ai_personalize_instructions(user_id, instruction_text, updated_at)  -- 有料のみ
notification_emails(user_id, email)                          -- メール配信機能を使うユーザーのみ
```

## パーソナライズAI要約の生成方式

現行の日次バッチ処理(全ユーザー共通の1本のダイジェストを生成する仕組み)はそのまま維持する。そのうえで、有料会員に対しては同じバッチ内で追加のGemini呼び出しを行う:

1. 共通バッチで取得済みの記事プールに、そのユーザーのカスタムフィードから追加取得した記事を合わせる(記事取得自体の大部分は再利用するためコスト増は限定的)
2. そのユーザーの`ai_personalize_instructions`をプロンプトに追加し、Geminiを1回追加呼び出しする
3. 結果を`users/{userId}/{date}.json`としてR2に保存する
4. 有料会員がログインしてサイトを見ると、共通ダイジェストの代わりにこの個人版を表示する

コスト面: 有料会員1人あたり1日1回の追加Gemini呼び出しのみで、Free Tierの範囲内で十分まかなえる規模である(既存の試算通り)。

## API/フロントエンド構成

- 現状のフロントWorker(`apps/frontend/worker/index.ts`、cron起動+静的配信のみ)を拡張し、**実際のAPIルーティングを持つWorker**にする(ログイン/コールバック/ログアウト、設定CRUD、ブックマークCRUD、Stripe関連)
- 既存の静的SSGページ(ダイジェスト本体)はそのまま維持する。ログイン状態・パーソナライズ設定・ブックマーク一覧などは、ページ読み込み後にブラウザから上記APIを叩いて動的に描画する(「静的HTML+一部だけ動的」という既存方針を踏襲)
- D1へのアクセスはこの新Workerからのみとし、バックエンド(Workers Builds側の生成処理)はR2のみ触る形で責務を分離する

## Stripe決済フロー(現時点ではスタブ実装)

**現時点でStripeアカウントを作成していないため、実装に着手する際はスタブとして進める。** `subscriptions`テーブル・課金状態のチェック処理はコード上に用意するが、実際のStripe Checkout/Webhook連携は、Stripeアカウント作成後に本実装へ差し替える。

想定する本実装のフロー(参考):
- 有料化ボタン押下 → Stripe Checkout Sessionを作成しリダイレクト(カード情報は一切こちらを通らない)
- Webhook(`checkout.session.completed` / `customer.subscription.updated` / `deleted`)をWorkerで受け、`subscriptions`テーブルを更新する。StripeのNode SDKは`constructEventAsync`によるWeb Crypto版のWebhook署名検証を公式サポートしており、Cloudflare Workers上でも動作する
- 解約・支払い方法変更はStripe Customer Portalへのリンクで対応し、自前でUIを作らない
